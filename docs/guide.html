Zero — Flow & Setup Guide

com.tnbao91.nobody.zero — an opinionated Unity 6 LTS template for hybrid-casual and puzzle games. This page describes what actually happens at runtime and exactly how to stand the template up in your own project.

Every fact on this page was read out of the code, not out of the prose docs. Where a behaviour is surprising, the source line is cited. If this page and a Markdown doc disagree, trust the code and file an issue — several docs were wrong about the pipeline until the review that produced this page.

1. What Zero is — and is not

Zero is the layer between "empty Unity project" and "your game": dependency injection, an ordered async bootstrap, ~24 service seams, a popup/screen/toast stack, and a save system that actually encrypts. It ships as a UPM package; your game lives outside it.

Three constraints worth knowing before you adopt it:

  • It is genre-agnostic on purpose. Zero.Gameplay ships a state machine, a level loader and lifecycle events — nothing else. Grid, runner, idle, merge and match-3 systems are yours to write, in your own assembly.
  • You own the scenes and the UI roots. Only Bootstrap.unity is in build settings. The framework never spawns a canvas; you attach a UIRoot component with four Transform slots and it wires itself in.
  • Third-party SDKs are mocks. Analytics, ads, IAP, attribution, consent, crash reporting and remote config all ship as Mock…Service implementations that log what they would send. You swap the binding per game. The only real implementations wrap packages Unity itself ships.

The stack is fixed and not up for substitution: Reflex (DI), UniTask (async), R3 (reactive), LitMotion (tweening), Newtonsoft.Json, ZString.

2. The boot flow

There is no ProjectContext prefab and no scene-based composition root. Wiring is code:

The 16 steps

Order is the literal defaultSteps array in ProjectScopeInstaller.cs:125-143. Names are the Name property on each step — you need the exact string to anchor your own step against one.

No shipped step is critical, and that is the design. Bootstrap never denies the player the game: a step that fails degrades a feature, and the pipeline runs on.

This is a deliberate reversal — DeviceProfile, Asset and Consent were critical until 0.6.0. The reason is below: an abort has nowhere good to land. A test pins the rule (BootstrapDegradationTests) so it cannot regress by accident.

The mechanism still exists for your steps. If your game genuinely cannot run without something — a server login, say — override IsCritical => true on your own step, and build the retry screen that has to go with it.

Why nothing is critical

Look at what an abort actually does. The pipeline stops, publishes BootstrapFailed, and GameLauncher writes one Debug.LogError. That's the end of it — nothing in the template subscribes to BootstrapFailed, and LoadingScreenView has no failure path. The retry UI that the design assumes is consumer work, and no sample provides it.

So in a stock project, "critical" does not mean a controlled stop. It means the splash screen sits there forever. For a hybrid-casual or puzzle game, where time-to-first-interaction is the number that decides whether a player ever comes back, that is the worst possible outcome — and it was being triggered by things like "quality settings failed to apply".

The fix isn't to swallow more failures, it's to stop pretending they didn't happen. A step that exhausts its retries now records itself in IBootstrapReport and publishes BootstrapStepDegraded. The player gets into the game; the game gets to decide what to switch off. 

[Inject] private IBootstrapReport _report;

private void Start()
{
    // The shop is the feature that needs IAP. Nothing else has to care.
    _shopButton.gameObject.SetActive(!_report.IsDegraded("IAP"));

    if (!_report.IsHealthy)
        _log.Warn($"Booted degraded: {_report.Degraded.Count} step(s) failed");
}

Use the bus event when you want to react at the moment of failure, and the report when you are asking after the fact — R3EventBus does not replay, so anything constructed after boot has already missed the event. That is exactly why the durable record exists alongside it.

Failure, retry and timeout

Read from BootstrapPipeline.cs:

  • Attempts are MaxRetries + 1 — MaxRetries counts additional tries, and defaults to 1, so a step runs twice before giving up. AssetStep overrides it to 2 (3 attempts), because a transient catalog fetch is the failure most worth retrying.
  • A step that exhausts its attempts is recorded, announced, and passed. The pipeline logs "exhausted N attempt(s); continuing degraded", calls IBootstrapReport.Record and publishes BootstrapStepDegraded(StepName, Error, Attempts).
  • A critical step — yours, not the template's — never retries. The first failure calls Abort(), which throws BootstrapStepFailedException and publishes BootstrapFailed. An abort is not recorded as a degradation; the two paths are distinct.
  • Timeout is cooperative, not a kill. Each attempt runs under a linked CancellationTokenSource with CancelAfter(step.Timeout). A step that ignores its token keeps running — the pipeline just stops waiting. UniTask and Addressables both respect it.
  • Outer cancellation always wins and is never retried.

Retry is consumer-triggerable: publish BootstrapRetryRequested and GameLauncher re-runs RunAsync(). The report is cleared at the start of every run, so a successful retry clears the degraded state. There is no completed-step tracking, so every step runs again — steps must be idempotent. Guard one-time side effects inside the service (if (_initialized) return;), not in the step.

Progress

Views read IBootstrapProgressReporter, never the pipeline. It exposes Observable<float> Progress, Observable<string> CurrentStepName, and — often missed when writing a custom reporter — a void Report(float, string) the pipeline calls.

Both the reporter and the pipeline are Lifetime.Singleton, Resolution.Lazy. The reason to inject the reporter is not availability, it is blast radius: resolving BootstrapPipeline constructs all 16 steps and every service they depend on. A loading bar should not trigger that.

3. Assembly map

One documented exception worth knowing. Zero.UI loads its prefabs through Unity.Addressables directly — it has no Zero.Services.Asset reference. Everywhere else the rule is "nothing calls Addressables directly, go through IAssetService". If you go looking for the IAssetService call in UIService, it isn't there; UIService, ScreenManager and ToastQueue each own their handle lifetime.

4. Setup, step by step

Step 1 — scoped registries

Add to your project's Packages/manifest.json:

"scopedRegistries": [
  {
    "name": "OpenUPM",
    "url": "https://package.openupm.com",
    "scopes": [
      "com.cysharp",
      "com.gustavopsantos",
      "com.annulusgames",
      "com.tnbao91",
      "com.github-glitchenzo"
    ]
  }
]

Step 2 — NuGetForUnity, before Zero

Package Manager → + → Add package by name → com.github-glitchenzo.nugetforunity. This is a prerequisite, not an optional extra: R3 needs four BCL DLLs that only NuGet can fetch.

Step 3 — install Zero

openupm add com.tnbao91.nobody.zero

Or Add package by name → com.tnbao91.nobody.zero.

Pin 0.2.1 or later — tags v0.1.0 and v0.2.0 are broken (a .gitignore collision dropped Runtime/Services/Log/ from the package).

Step 4 — import the Bootstrap Scene sample

Package Manager → Zero — Hybrid Casual Template → Samples → Import next to "Bootstrap Scene". Files land in Assets/Samples/com.tnbao91.nobody.zero/<version>/BootstrapScene/. Then, by hand:

  • Move Bootstrap.unity to your scenes folder and add it to Build Settings.
  • Move ReflexSettings.asset to Assets/Resources/ReflexSettings.asset. Its root-scopes list is intentionally empty — wiring is code, not data.
  • Copy packages.config to Assets/packages.config, then NuGet menu → Restore Packages.

The sample also contains a link.xml. No setup step currently tells you where to put it — if you strip assemblies on IL2CPP, merge its entries into your own Assets/link.xml.

Step 5 — save encryption seeds

Copy ZeroSecrets.asset.example to Assets/Resources/ZeroSecrets.asset, open it, and replace both _aesSeed and _hmacSeed. Both ship as the literal string REPLACE_BEFORE_SHIPPING.

Player builds throw InvalidOperationException at startup if either seed is still the placeholder. The Editor only warns, so iteration is not blocked — which means it is entirely possible to develop for weeks and discover this in your first device build. Do it now. The file is gitignored; keep the values in your team's secret manager.

Step 6 — press Play

Open Bootstrap.unity → Play. The Console prints [Bootstrap] Step N/16: … for each step. If you see 16 lines and no red, the template is correctly installed.

5. Two honest milestones

It is worth being precise about what the shipped sample gets you, because the gap between the two milestones below is where adopters lose an afternoon.

reachable Bootstrap running — about 15 minutes

Steps 1–6 above and nothing else. Every third-party service defaults to a mock, so nothing needs credentials, and AssetStep initializes the Addressables runtime without requiring any content to exist. You get a booted container and 16 green log lines.

not reachable from the sample A popup on screen — add 30–60 minutes

The Bootstrap scene contains a camera and a splash background. There is no UIRoot, no canvas hierarchy, no popup prefab, and no Addressables group anywhere in the template, and no sample demonstrates them. To get one popup up you must:

  1. Create a scene with a [UI] GameObject and four child canvases — [UI.Hud] (sortOrder 100), [UI.Popup] (200), [UI.Overlay] (300), [UI.System] (400).
  2. Add the UIRoot component and drag those four Transforms into its slots.
  3. Write a popup deriving from PopupBase<TData, TResult> and build a prefab from it.
  4. Create an Addressables group and mark the prefab addressable at exactly ui/popup/<your class name, lowercased>.
  5. Resolve IUIService and call PushAsync<TPopup, TData, TResult>(…).

The full canvas recipe is in docs/ui/ui-root.md.

6. Extending it

Swapping a service implementation

From your own assembly, hook the root container build. Because the package hooks at BeforeSplashScreen and you hook at BeforeSceneLoad, your registration lands later and Reflex resolves the last one. 

public static class MyGameInstaller
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
    private static void Hook()
        => ContainerScope.OnRootContainerBuilding += Install;

    private static void Install(ContainerBuilder builder)
    {
        builder.RegisterType(
            typeof(FirebaseAnalyticsService),
            new[] { typeof(IAnalyticsService) },
            Lifetime.Singleton,
            Resolution.Lazy);
    }
}

Do not try to extend via the partial seam. ProjectScopeInstaller is a partial class with an InstallUserBindings hook, and it works only if you forked the repo. C# partials must live in the same assembly, and a UPM consumer's package folder is read-only — you cannot add a file to it. The two real seams are OnRootContainerBuilding and BootstrapStepRegistration.

Adding your own bootstrap step

Subclass BootstrapStepBase and override OnExecuteAsync — the protected one. ExecuteAsync is the base's, and it brackets your work with progress.Report(0f) / Report(1f). 

builder.RegisterFactory<BootstrapStepRegistration>(
    c => new BootstrapStepRegistration(
            new MyLiveOpsStep(c.Resolve<IRemoteConfigService>()),
            BootstrapStepAnchor.After,
            "RemoteConfig"),
    new[] { typeof(BootstrapStepRegistration) },
    Lifetime.Singleton,
    Resolution.Lazy);

Anchors are Append, Before, After and Replace. The anchor name is matched against IBootstrapStep.Name with StringComparison.Ordinal and throws ArgumentException if not found — a typo fails loudly at startup rather than silently dropping your step. Use the exact strings from the table in §2.

Compile-time mock swap

Three services ship both a real and a mock implementation, selected by a define symbol rather than a binding — useful for headless test runs and CI:

7. Addressables key conventions

The UI stack builds its keys by convention — nothing is registered, so a mismatch surfaces as a missing asset at runtime, not a compile error. These strings come from the source, not the docs:

WhatKeyBuilt at
Popup prefabui/popup/{typeof(TPopup).Name.ToLowerInvariant()}UIService.cs:152
Screen prefabui/screen/{typeof(TScreen).Name.ToLowerInvariant()}ScreenManager.cs:42
Toast prefabui/toast/default — fixed, one prefab for all toastsToastQueue.cs:21
Audio mixeraudio/main_mixerdocs/services/audio.md
Music / SFX clipsaudio/music/<name> · audio/sfx/<name>docs/services/audio.md

Class name, lowercased — including the suffix. A popup class SettingsPopup needs the key ui/popup/settingspopup, not ui/popup/settings. Rename the class and the key silently stops matching.

It exists so the purchase→reward path compiles end-to-end during prototyping. Shipping it means any client that can call your purchase flow can grant itself every item in the game. Replace it with server-side validation before you take money.

9. The event bus

IEventBus is how the peer tiers talk without referencing each other. Two methods: Observable<T> On<T>() and void Publish<T>(T evt), backed by a dictionary of R3 Subject<T> behind a lock.

Two properties that bite if you assume otherwise:

  • Keyed by exact type. There is no polymorphic dispatch — subscribing to a base type will not receive a derived one.
  • No replay. A subscriber that arrives after a publish gets nothing. For bootstrap events in particular, subscribe in Awake/Start of something with an execution order early enough to beat the publisher.

Events that actually ship

EventAssemblyPublished when
BootstrapStepDegraded(StepName, Error, Attempts)Zero.CoreA step exhausted its retries. The pipeline continues; the durable equivalent is IBootstrapReport.
BootstrapFailed(StepName, Error, Attempt)Zero.CoreA critical step aborted the pipeline. No shipped step is critical, so this only fires for steps you add.
BootstrapRetryRequestedZero.CoreYou publish it; GameLauncher re-runs the pipeline.
PopupOpened · PopupClosedZero.CoreUIService pushes / pops the popup stack.
PopupBackdropTappedZero.CoreThe user taps outside a popup.
LevelStarted · LevelCompleted · LevelFailed · LevelExited · LevelRestartedZero.GameplayLevel lifecycle transitions.

There is no app-lifecycle event. AppPaused and AppQuitting appear in older docs and in the original plan, but no such type ships. Define your own POCO and publish it from a MonoBehaviour's OnApplicationPause — see docs/liveops/version-check.md for a working example.
